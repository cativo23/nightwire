# Migrating from v2 to v3

v3 is a major release. It replaces the look of every component, removes the v1 compatibility
surfaces that v2 kept, changes some values in the Tailwind preset, and makes the package an ES
module. The identity is unchanged: the four typefaces, the kanji labels and the three intensities
(`archive`, `operator`, `combat`). File names and locations in the package are unchanged too.

Who has to act:

- **CSS classes, hand-written CSS or the installer:** go through the checklist below.
- **Tailwind preset:** also read [Tailwind preset](#tailwind-preset) and
  [Package module type and the installer](#package-module-type-and-the-installer).
- **Not ready for v3:** [stay on v2](#staying-on-v2). v2.x stays available on npm.

For the reasons behind each visual value, see
[docs/design/v3/direction.md](../design/v3/direction.md). For the release notes in order, see
[CHANGELOG.md](../../CHANGELOG.md).

## Checklist

Run through these in order. Each item links to its section.

1. Search your markup for the removed classes and replace them
   ([Removed v1 surfaces](#removed-v1-surfaces)): `.led.green|blue|red|yellow`, `.tag-warning`,
   `.nw-progress .fill`, `.stack`.
2. Search your CSS for `--nw-header-gradient` and `--nw-header-pattern` and delete them
   ([Removed knobs and renamed documentation names](#removed-knobs-and-renamed-documentation-names)).
3. If you set `--nw-glow` on a single element to change an LED, control or progress glow, set
   `--nw-led-glow`, `--nw-control-glow` or `--nw-progress-glow` there instead
   ([Glow](#glow)).
4. If you use `.cmdk` without `.cmdk-backdrop`, check it still sits where you want
   ([Overlays](#overlays)).
5. Give every tooltip trigger `aria-describedby` and every tooltip content `role="tooltip"`
   ([Tooltips](#tooltips)).
6. If you use the Tailwind preset in a CommonJS config, change `require(...)` to
   `require(...).default` ([Package module type and the installer](#package-module-type-and-the-installer)).
7. If you re-ran the installer in an old project, point the Tailwind config at
   `nightwire.tailwind.preset.mjs` and delete the old `.js` copy.
8. If you use `shadow-glow-*` with `shadow-<colour>`, or `theme(colors.x/50%)`, or `bg-nw-*-fill`
   with an opacity modifier, adapt them ([Tailwind preset](#tailwind-preset)).
9. Look at every page once at the intensity you ship. The look changes everywhere
   ([Visual and motion changes](#visual-and-motion-changes)).

## Visual and motion changes

These are **breaking** for anyone who relies on the old look or on literal values. The full list of
values, with the old ones, is in CHANGELOG `[Unreleased]` under Changed.

### Overall look

v3 is neutral first: text, labels and edges are neutral, and colour appears where it means
something (data, state, focus, the selected item).

- Square corners: `.btn`, inputs, `.tag`, `.modal`, `.card`, `.combo`, `.cmdk`, `.dropdown-menu`,
  `.tooltip-content` and `.diff` use `--radius-sm` (2px). A `.tag` was fully round.
- Thin hairlines: every structural border reads `--nw-hairline` (1px). `--nw-line-strong` is 0.36
  (was 0.18), the 3:1 boundary used by form controls, check, switch, modal, dropdown, tooltip and
  toast.
- Labels (panel, card, modal and sidebar headers, table headers, field labels, stat and metric
  labels) are `--nw-text-mute`. They were blue. Stat and metric values stay green.
- `.btn` is a solid bone (`--nw-action`, black text) and was blue. `.btn-chrome` is now the only
  blue solid. `.btn-ghost` is an outline. Default `.tag` and `.badge` are neutral; blue is
  `.tag-chrome`.
- Glow is for state only (see [Glow](#glow)). The panel header gradient and scanlines are gone.

**How to adapt:** if you want a blue primary button, use `.btn-chrome`. If your CSS or tests assert
the old literal values (radii, alphas, colours), update them from the CHANGELOG.

### Glow

`--nw-glow` is 0.5 at operator (was 1) and 0 at archive. Combat no longer overrides it (it was
2.2). The decorative glows are gone: the `.btn-success` and `.btn-ai` resting shadow, and the
`text-shadow` on `.stat-value`, `.m-value` and the AI-block glyph. The `.glow-*` text classes now
read `--nw-glow` and are weaker: alpha 0.33 and 0.13 (was 0.5 and 0.2; red's second layer is 0.2,
was 0.3).

State signals (LED, check, radio, switch, segmented, steps, progress) read their own knob:
`--nw-led-glow`, `--nw-control-glow` and `--nw-progress-glow`. Each is `var(--nw-glow)` resolved on
`:root`, and combat doubles each, so at combat they reach an effective 1, still below the 2.2 of v2.

**Behaviour change:** a `--nw-glow` set on `:root` (or on the element with `data-intensity`) still
reaches them. One set on a single element no longer does, because in v2 `.led` read `--nw-glow`
directly.

**How to adapt:** set `--nw-led-glow`, `--nw-control-glow` or `--nw-progress-glow` on that element.

### Motion

- **Overlays animate on open and close.** The drawer, modal, command palette, dropdown, toast and
  tooltip fade and slide when they open, and run an exit (`--nw-sweep-out`, `--nw-tick-out`) when
  they close, instead of snapping shut. A closed drawer, modal or command palette is hidden: not
  clickable, not focusable, not in the accessibility tree. First paint does not animate. Browsers
  outside the latest 2 versions of Chrome, Edge, Firefox and Safari open and close instantly.
- **`data-open` on dropdown, toast and tooltip.** `data-open="false"` closes the dropdown and the
  toast with an exit animation. Without the attribute they stay open, as in v2. A tooltip with
  `data-open="true"` is pinned open, with `"false"` it stays closed even on hover, and without the
  attribute it opens on hover as before.
- **Durations follow the intensity.** Hover, focus and press feedback run on `--nw-tick`, and
  multiply by `--nw-motion-scale` (archive 0.6, combat 1.2) where v2 used fixed values. At operator
  the button press transition is 150ms where it was 100ms, and the easing is the `--nw-tick` curve
  rather than `ease`.
- **Loops follow the intensity.** The button spinner, the skeleton shimmer and the LED pulse divide
  their cycle by `--nw-motion-scale`: archive loops run slower, combat loops faster.
  `--nw-pulse-speed` is 1.6s (was 1.4s) with no combat override (was 0.7s).
- **Reduced motion wins over every intensity.** In v2, `data-intensity="archive"` or `"combat"`
  beat the reduced-motion block. In v3 `prefers-reduced-motion: reduce` sets the scale to 0 and
  pauses the loops at every level.

**How to adapt:** nothing in your markup. Re-test any check that expects an overlay to be hidden
the instant it closes: the closed state now arrives after the exit animation, and reduced motion
removes the wait.

### Overlays

The `.cmdk` start-position transform is now scoped to `.cmdk-backdrop .cmdk`. A standalone `.cmdk`
with no backdrop to open it stays where it was in v2. `.modal`, `.drawer` and `.cmdk` take
`--nw-elevation-overlay` and a `--nw-line-strong` border, and the open modal has no residual
`transform`.

**How to adapt:** put `.cmdk` inside `.cmdk-backdrop`, or check that a standalone one still
renders where you expect.

### Toast

The left accent is 2px (`--nw-accent-width`, was 3px), and the toast has a 1px `--nw-line-strong`
boundary on the top, right and bottom. The `.toast-*` variants still colour the accent. A closed
toast (`data-open="false"`) is hidden and not clickable.

### Tooltips

A closed `.tooltip-content` is now `visibility: hidden`, so its text is out of the accessibility
tree until the tooltip opens (in v2 it was in the tree, at opacity 0). `.tooltip` also opens on
`:focus-within`, so it opens on keyboard focus.

**How to adapt:** give the trigger `aria-describedby` pointing at the content's `id`, and the
content `role="tooltip"`. `aria-describedby` still reads hidden content, so the description
survives.

## Removed v1 surfaces

v2 kept the v1 spellings working next to the v2 ones. v3 removes them. The reasons and the places
in `src/` are in [docs/design/v3/v1-inventory.md](../design/v3/v1-inventory.md).

| Removed | Replacement | Note |
|---|---|---|
| `.led.green` | `.led[data-state="ok"]` | Not pixel-identical, see below. |
| `.led.yellow` | `.led[data-state="warn"]` | |
| `.led.red` | `.led[data-state="error"]` | |
| `.led.blue` | `.led[data-state="active"]` | v2 had no blue state. `active` is new in v3 and uses `--nw-chrome`. |
| `.tag-warning` | `.tag-warn` | It was always the same colour and fill. |
| `.nw-progress .fill` | `.nw-progress-fill` | v2.1.0 called it a deprecation candidate for v3. |
| `.stack` | `.nw-stack` | Same at default density; `.nw-stack` also honours `--nw-density`. |
| `.modal-backdrop` always-visible rule | one `.modal-backdrop` rule, closed by default | Dead code merged. Rendering does not change; nothing to adapt. |

The LED migration is not pixel-identical: the v1 glow was `4px * --nw-glow`, and the state glow in
v3 is `8px * --nw-led-glow`. At operator both come out as a 4px blur (checked on cativo.dev, whose
LEDs compute the same colours and the same shadow before and after); at archive the LED has no glow,
and at combat the two differ.

**How to adapt:** find and replace the classes. `.stack` is a common name, so check that you are
replacing Nightwire's class and not your own rule. An LED coloured by a dynamic binding
(`:class="ok ? 'green' : 'red'"`, or a map from status to class) moves to `:data-state`; keep any
class of your own, such as a blink, in `class`. A plain `.led` with no colour class has no colour in
v2 or v3, so leave `data-state` unset for that state.

Kept on purpose, so no change is needed: `.modal-header`, `.badge-warning`, `.toast-warning`,
`.text-warning`, `.tag-info`, `.tab.active`, `.sidebar-item.active`, `.grid-2|3|4`, and dropdown and
toast being open when `data-open` is absent.

## Removed knobs and renamed documentation names

### Knobs

| Removed | Why | How to adapt |
|---|---|---|
| `--nw-header-gradient` | Panel headers have no gradient at any intensity. | Delete your references. |
| `--nw-header-pattern` | Panel headers have no scanlines at any intensity. | Delete your references. |
| Combat `--nw-glow` of 2.2 | Combat no longer overrides the glow. | See [Glow](#glow). |
| Combat `--nw-pulse-speed` of 0.7s | Combat pulses through the motion scale, in 1.333s. | Nothing. |

### Documentation names

`DESIGN.md` in v2 listed motion as `duration-fast` (150ms), `duration-base` (250ms),
`duration-slow` (400ms), `easing-standard` and `easing-decelerate`. They were documentation only:
no CSS custom property or preset key had those names. v3 lists the real motion properties in the
generated `motion` region instead: `--nw-tick`, `--nw-sweep`, `--nw-uplink`, their `-out` forms, the
`-duration` and `-ease` longhands, `--nw-stagger`, `--nw-loop-spin` and `--nw-loop-shimmer`. They
were replaced, not renamed one for one.

**How to adapt:** if you copied a value from those names, read the matching `--nw-*` property
instead. The ticker-scroll and led-blink animations, listed in `DESIGN.md` without any CSS behind
them, are gone from the document too.

## Tailwind preset

The preset now follows the custom properties, so utilities follow `data-intensity` and runtime
overrides (K3). Colours are
`color-mix(in srgb, var(--nw-x) calc(<alpha-value> * 100%), transparent)`, which keeps opacity
modifiers such as `bg-nw-cyan/40` generating. `duration-nw-*` and `ease-nw-*` are
`var(--nw-*-duration)` and `var(--nw-*-ease)`, so they scale with `--nw-motion-scale` and drop to 0
under reduced motion. New keys: `duration-nw-{tick,sweep,uplink}-out`,
`ease-nw-{tick,sweep,uplink}-out`, and `nw.action.DEFAULT|hot|text`. Font families, sizes, letter
spacing, spacing and radii stay literal. The exact strings are in `tailwind.preset.js`.

Four things need a check.

### `shadow-glow-*` changed value

`shadow-glow-{green,blue,cyan,red}` use the same string as the `.glow-*` classes. They go from a
fixed `8px` and `16px` blur at alpha `0.5` and `0.2` (red's second layer `0.3`) to `4px` and `8px`
at `0.33` and `0.13` (red `0.2`) at operator, and none at archive.

**How to adapt:** nothing, unless you relied on the old strength. Use them for state only.

### `shadow-<colour>` no longer recolours `shadow-glow-*`

In v2, adding a `shadow-<colour>` utility next to `shadow-glow-*` recoloured the glow. In v3 the
combination renders no glow. The v2
`--tw-shadow-colored` was `0 0 8px var(--tw-shadow-color), 0 0 16px var(--tw-shadow-color)`; the v3
one is `0 0 var(--tw-shadow-color), 0 0 var(--tw-shadow-color)`. Tailwind 3 does not read
`calc(...)` as a length, so it drops the blur (checked on Tailwind 3.4.19).

**How to adapt:** do not combine them. Keep the default glow colour, or write an arbitrary
`shadow-[…]` value.

### `theme()` and the slash form

A plain `theme(colors.nw.cyan.DEFAULT)` inside an arbitrary value still works: it resolves
`<alpha-value>` to 1, so `shadow-[0_0_5px_theme(colors.nw.cyan.DEFAULT)]` computes to a valid
colour (checked on Tailwind 3.4.19 with Chrome). The slash form `theme(colors.x/50%)` becomes
`calc(50% * 100%)`, which is invalid at computed time, and the property falls back (for example
`box-shadow: none`).

**How to adapt:** use an opacity utility (`bg-nw-cyan/50`) or write `color-mix` directly.

### Tokens that carry their own alpha

`bg-nw-primary-fill`, `-green-faint`, `-green-fill`, `-cyan-glow`, `-red-fill`, and the faint, line,
`line-strong` and `line-chrome` colours now multiply with an opacity modifier. `bg-nw-primary-fill/40`
is 0.4 × 0.08, where v2 replaced the alpha. `border-nw-text-faint/30` was white at 0.3 in v2 and is
white at 0.024 in v3 (the token is white at 0.08), so a hairline written that way nearly vanishes.

**How to adapt:** for the v2 look, write the colour you meant (`border-white/30`).

## Package module type and the installer

`package.json` has `"type": "module"`. The reason is that `tailwind.preset.js` is an ES module, and
Node now agrees: `import preset from '@cativo23/nightwire/tailwind.preset.js'` loads without a
`MODULE_TYPELESS_PACKAGE_JSON` warning. The CLI stays CommonJS through `dist/package.json`. File
names and locations are unchanged, and `exports` and `engines` are still not declared.

**A CommonJS Tailwind config must use `require('@cativo23/nightwire/tailwind.preset.js').default`.**
A bare `require()` returns the module namespace, and Tailwind 3.4 drops it without an error: no
`nw-*` utility is generated. The "No utility classes" warning appears only when nothing else in
your source matches. A dynamic `import()` cannot work in a CommonJS config, because Tailwind's
`loadConfig` is synchronous.

```js
// tailwind.config.js (CommonJS)
module.exports = {
  presets: [require('@cativo23/nightwire/tailwind.preset.js').default],
};
```

An ESM config needs no change.

Checked on Node 24.15 with Tailwind 3.4.19, and with `--no-experimental-require-module` to simulate
Node without `require()` of ES modules (before 20.19 and 22.12). It was not checked on an older
Node. There, Tailwind 3.4 catches `ERR_REQUIRE_ESM` and loads the config through jiti, where
`.default` also works.

**The installer writes `nightwire.tailwind.preset.mjs`** (it was `.js`). A `.mjs` file is always an
ES module, so there is no module-type warning even in a project without `"type": "module"`.
Re-running the installer in an old project leaves the old `.js` copy behind.

**How to adapt:** point the Tailwind config at the `.mjs` file and delete the old `.js` copy.

## Known limits

- **Sub-tree overrides.** Preset utilities and the `.glow-*` classes read their custom property
  where they are used, so a colour token or `--nw-glow` set on a sub-tree reaches them. The LED,
  control and progress glow do not follow a single-element `--nw-glow` (see [Glow](#glow)).
  `--nw-motion-scale` and the input of an alias token (`--nw-primary` for `--nw-chrome`) resolve on
  `:root`, so they follow only when set on `:root` or on the `data-intensity` element. To change one
  on a sub-tree, override the derived token itself (`--nw-chrome`).
- **`shadow-<colour>` with `shadow-glow-*`** renders no glow (see above).
- **`theme(colors.x/50%)`** is invalid with the preset (see above).

## Staying on v2

v2.x stays available on npm. To keep v2:

```sh
npm install @cativo23/nightwire@^2
```


## Not affected

`blog.cativo.dev` vendors a v1.0.x copy of the CSS and has no Tailwind, so it is not affected by
v3. Nothing in this guide applies to it unless you update that copy.

## cativo.dev

cativo.dev is the one production consumer that uses both the classes and the Tailwind preset (through
the `.nightwire` submodule, pinned at `021ae0c`, between v2.0.1 and v2.1.0). It was validated on
2026-11-19 against `feat/002-migration` at `7309061`; the later commits there only touch this guide
and its test.

**How.** Three copies of the portfolio ran in the Nuxt dev container (Tailwind 3.4.17): `021ae0c`
(v2), v3 unchanged, and v3 with the changes below. Headless Chrome walked all 16 routes under
`src/pages` at 1280 wide (the admin ones with `/api/admin/me` mocked), and `/` and `/cv` again at
390. The backend was not running, so API sections show their empty or error state on all three.

**Result.**

- Pages: 0 broken. No horizontal overflow at 390, no text with the colour of its background, no
  console error that differs between versions, and the same page height in all three on every
  route. Every page that uses a Nightwire component shows the v3 look (neutral panel headers, a bone
  `.btn`, no header gradient); `/cv` differs by under 0.1% of its pixels.
- Utilities: Tailwind output for the portfolio's content with the `021ae0c`, `v2.1.0` and v3 presets
  is 625 selectors each, **0 lost, 0 gained**. That includes the same 29 colour utilities with an
  opacity modifier (22 `/NN`, 7 `/[0.NN]`), and no declaration with an invalid-looking value
  (`calc(NN% * 100%)`, empty `var()`). 86 selectors keep their name and change their colour
  declaration, as described under [Tailwind preset](#tailwind-preset).
- `theme()`: `shadow-[0_0_5px_theme(colors.nw.cyan.DEFAULT)]` (`layouts/admin.vue:26`) computes to a
  valid cyan glow on `/admin`.
- The config is ESM, so the preset import needs no `.default`.

**What cativo.dev needs.** The LEDs are the only required change: on v3 they lose their colour and
glow. Replace, then check at the intensity you ship:

- [ ] `components/home/LatestPosts.vue:7`, `components/home/Hero.vue:28`,
  `components/main/Header.vue:30,83`, `pages/about.vue:32`, `pages/admin/index.vue:25`:
  `led green blink` becomes `led blink` with `data-state="ok"`.
- [ ] `components/chat/Widget.vue:71,93`: `led blue blink` becomes `led blink` with
  `data-state="active"`.
- [ ] `components/home/ProofOfWork.vue:68`: the `'green' : 'red'` class binding becomes
  `:data-state` with `'ok' : 'error'`.
- [ ] `components/ui/StatusIndicator.vue:7,31-35` (used by `ui/HealthBadge.vue:5` and
  `pages/health.vue:31,50`): the status map becomes `ok`, `error`, `warn`, `active` and `''`, bound
  as `:data-state="state || undefined"`.
- [ ] `components/main/Footer.vue:21,105-109`: `green blink`, `yellow blink` and `red` become the
  states `ok`, `warn` and `error`; keep `blink` in `class` for the first two only.

`.led.blink` (`assets/css/main.css:166`) is cativo.dev's own and stays. With these changes every
LED computes the same colour and the same 4px shadow as on v2.

One more, not required for layout:
